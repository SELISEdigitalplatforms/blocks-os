# Blocks OS; End-to-End Tests (Playwright)

E2E tests that drive the real app through the browser, including the dev-iam
login redirect flow.

## One-time setup

1. **Configure env**: copy the template and fill in your values:

   ```bash
   cd e2e
   cp .env.e2e.example .env.e2e
   ```

   Set `E2E_BASE_URL` (your named domain, e.g. `https://dev-os.blocksdevelopers.com:5000`),
   `E2E_USERNAME`, `E2E_PASSWORD`. `.env.e2e` is gitignored; never commit real
   credentials.

2. **Install** Playwright + the browser:
   ```bash
   cd e2e
   npm install
   npx playwright install chromium
   ```

## Run (single command)

```bash
cd e2e
npm test
```

That's it. `npm test` will:

1. start the app via `run.sh -a` from the repo root (builds the FE, syncs to
   `server/Api/wwwroot`, runs API + Worker),
2. wait until `E2E_BASE_URL` responds (up to 10 min for the first build),
3. run the tests, then
4. shut the server down.

If the app is **already** running at `E2E_BASE_URL`, it is reused (no rebuild).

> Auto-start uses `bash run.sh -a`, so **Git Bash's `bash` must be on PATH**
> (`run.ps1 -a` can't be automated). To manage the server yourself instead, run
> it manually and start tests with auto-start disabled:
>
> ```bash
> E2E_NO_WEBSERVER=1 npm test
> ```

### Other run modes

```bash
npm run test:headed   # watch it in a real browser
npm run test:ui       # Playwright UI mode
npm run report        # open the last HTML report
```

## Manual selector inspection

The normal E2E update workflow is the graph workflow below. Use Playwright
codegen only for manual inspection when selectors are unclear or a live page
needs verification.

The username/password fields live on the dev-iam page. To inspect selectors
against the live page:

```bash
npm run codegen -- <E2E_BASE_URL>/login
```

## E2E graph workflow for humans and AI

The E2E graph maps app surfaces, user actions, and coverage. Humans and AI agents must use it when deciding whether frontend changes need E2E updates or when writing new AI-authored E2E.

Normal frontend task check:

```bash
npm run graph:impact
```

Full graph audit, only when requested:

```bash
npm run graph:inventory
npm run graph:check
```

Render generated graph docs and refresh the local selector cache:

```bash
npm run graph:render
```

Apply graph additions through the patch protocol:

```bash
npm run graph:update -- --patch e2e/graph/patch.json
```

All graph commands and agent summaries use:

```text
verdict: <none|possible|likely|definite|unknown|pass|warning|fail|approval-required>
reason: <short concrete reason>
next: <next action or "none">
```

`flow-graph.json` is the graph source of truth. `flow-graph.md` and `selector-index.json` are generated by `npm run graph:render` and do not need to be committed.

Flow coverage is the main E2E signal. A flow proves a user can complete a business path
and observe the resulting UI or backend-visible state. Journey specs are still useful,
but only as page-smoke or route evidence; they do not close primary flow coverage gaps.

AI-authored smoke coverage must follow the rules in this section. New generated smoke
coverage goes under:

```text
e2e/support/steps/<domain>.steps.ts
e2e/tests/journeys/<journey>.spec.ts
```

Create those directories only when the first generated journey is needed. Do not add new AI-authored coverage to legacy paths unless the user explicitly approves:

```text
e2e/tests/flow/
e2e/tests/auth/
e2e/tests/secrets-and-configs/
e2e/support/navigation.ts
e2e/support/console.ts
e2e/support/flow-state.ts
```

### Graph source files

```text
e2e/graph/flow-graph.json          source of truth
e2e/graph/uncovered-baseline.json  uncovered-node classification
e2e/graph/flow-graph.md            generated Mermaid, gitignored
e2e/graph/selector-index.json      generated local selector cache, gitignored
```

### Impact evaluation order

This order is mandatory:

```text
1. If no client/app/** files changed -> none
2. If Git diff is unavailable -> unknown
3. If router.tsx or navigation-menus.ts changed -> definite
4. If touched client/app files contain an action keyword in a user-action surface -> likely
5. If selector-index.json is missing or stale -> unknown
6. If diff removes/alters a string in selector-index.json -> definite
7. Otherwise -> possible
```

Cache-independent signals are evaluated before selector cache checks. Missing or stale `selector-index.json` returns `unknown` only when no stronger cache-independent signal was found.

Action keywords:

```text
delete
cancel
invite
grant
revoke
approve
reject
submit
confirm
upload
sync
save
create
update
remove
```

Only count keywords inside likely user-action surfaces:

```text
JSX visible text
aria-label
title
placeholder
label
name
button/link/menu labels
handler names like onSubmit, handleDelete, onInvite
route/action config labels
```

### Graph node and metadata rules

Graph node IDs are derived from slugified canonical routes, never menu IDs.

Example:

```text
/app/project/:tenantGroupId/settings -> app-project-tenantGroupId-settings
/app/:itemId/idp/settings            -> app-itemId-idp-settings
```

`flow-graph.json` includes metadata:

```json
{
  "metadata": {
    "schemaVersion": 1,
    "lastUpdatedAt": "ISO timestamp",
    "lastUpdatedBy": "graph-update.js",
    "contentHash": "sha256:<hash>"
  },
  "nodes": [],
  "edges": []
}
```

`contentHash` is SHA-256 over the canonical graph payload excluding `metadata.contentHash`.

Canonical serialization:

```text
recursively sort object keys alphabetically
preserve array order
JSON.stringify with no whitespace
UTF-8 bytes
no trailing newline
```

### Uncovered baseline rules

`uncovered-baseline.json` statuses:

```text
backlog
needs-e2e
needs-flow
no-e2e-needed
covered-by-parent
```

Coverage must be evidence-based:

- A route has primary flow coverage only when a flow-style E2E test directly visits it or
  reaches it through browser actions, then asserts both the URL and route-specific UI state.
- An action has primary flow coverage only when a flow-style E2E test performs the action
  and verifies the resulting UI or backend-visible state.
- `e2e/tests/journeys/*` specs provide smoke evidence only. They can prove a route renders
  and can document selectors/assertions, but they do not remove a node from
  `uncovered-baseline.json`.
- Use `needs-flow` when a node has journey/smoke evidence but still lacks primary flow
  coverage.
- `covered-by-parent` is allowed only for non-addressable index/layout redirects or a child
  state that the named parent test actually enters and asserts. Do not use it for nested
  detail routes that a parent/list-page smoke test merely implies.
- If the route has any dynamic URL segment, meaning any path segment that starts with
  `:`, mark it `needs-e2e` until a test reaches that exact URL shape and asserts
  route-specific content.
- If the evidence is only "should be covered through..." or "covered by broader journey",
  the correct status is `needs-e2e`, not `covered-by-parent`.
- Any graph edge targeting a dynamic route must include evidence:

  Example shape only; use the route pattern and assertions from the actual test:

  ```json
  {
    "evidence": {
      "urlPattern": "/resource/.+/detail/.+",
      "assertions": ["Detail page heading"]
    }
  }
  ```

- Any graph edge that performs more than navigation/open/login must include result evidence:

  Example shape only; use the real action type, route pattern, assertions, and result
  observed by the test:

  ```json
  {
    "actionType": "create",
    "evidence": {
      "urlPattern": "/resource/.+",
      "assertions": ["Created item name"],
      "result": "Created item is visible in the list or can be read from the backend."
    }
  }
  ```

`graph:check` behavior:

```text
backlog                         informational
no-e2e-needed                   informational
covered-by-parent               informational
needs-e2e                       warning
needs-flow                      warning
journey/smoke only              warning
dynamic route covered-by-parent warning
dynamic edge missing evidence   warning
action edge missing result      warning
unclassified                    warning
orphaned baseline entry         failure
baseline entry already covered  failure
stale graph node                failure
broken graph reference          failure
protected legacy path dirty     warning
```

`uncovered-baseline.json` may contain nodes without primary flow coverage. If a node
becomes covered by a flow-style test, remove it from `uncovered-baseline.json`.
`graph-update.js` removes baseline entries only for nodes newly covered by a primary
flow-style patch. Journey/smoke patches stay in the baseline as `needs-flow` until a
real flow covers them.

### Legacy E2E approval rule

Read legacy E2E freely, but do not modify it unless the user explicitly approves.

If a graph or coverage fix appears to require modifying one of the protected legacy paths, stop and ask:

```text
verdict: approval-required
reason: required change touches protected legacy E2E
next: ask user whether to modify legacy E2E or keep it as-is
```

If the user approves a legacy E2E graph patch, run:

```bash
npm run graph:update -- --allow-legacy
```

`graph:update` rejects new edges that do not meet the evidence rules above. New
journey-backed edges must set `"coverageLevel": "smoke"` so they cannot be mistaken for
primary flow coverage. Existing edges without evidence are reported by `graph:check` as
warnings until they are updated or downgraded from covered graph edges.

## The flow suite; one project per run

`tests/flow/*` is a **single sequential scenario**, not independent tests. Step 01
creates one project and records its name + `tenantGroupId` in
`fixtures/flow-state.json`; every later step reads that id, so they all act on the
**same** project. Step 06 deletes it again.

```
01 create project (Development + Testing)
02 add environment  (Staging)
03 invite a person  (Development)
04 grant that person access to Testing
05 add an application domain
06 delete the project   <- teardown
```

Because they share state they must run in order, which is why `workers: 1` and the
numeric filename prefixes exist. Running one step alone fails fast with
"run 01-create-project first".

Knobs in `.env.e2e`:

| Variable             | Effect                                                                                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `E2E_PROJECT_NAME`   | Name for the run's project. **Blank = `e2e-<random>` per run** (recommended; repeated runs never collide). Set a value when you want a predictable project to inspect.            |
| `E2E_KEEP_PROJECT=1` | Skip step 06, leaving the project behind.                                                                                                                                          |
| `E2E_NO_WEBSERVER=1` | Don't auto-start the app; you manage the server.                                                                                                                                   |
| `E2E_PAUSE_MS`       | How long the browser holds after **each** test so you can see the result. Defaults to **10 s in headed mode**, 0 when headless. Set a number to override either way; `0` disables. |
| `E2E_SLOWMO`         | Milliseconds of delay per action, to watch the steps themselves.                                                                                                                   |

```bash
E2E_PROJECT_NAME=e2e-demo E2E_KEEP_PROJECT=1 npm run test:headed
```

> Nothing in the suite scans the console for "some `e2e-*` project" any more; a run
> only ever touches the project it created itself.

## Layout

```
e2e/
  tests/auth/login.spec.ts   # login through dev-iam -> /app/console
  tests/flow/01..06          # the sequential scenario above
  support/flow-state.ts      # shared project reference between steps
  fixtures/                  # auth storage state + flow state (gitignored)
  playwright.config.ts       # baseURL + creds from .env.e2e
```
